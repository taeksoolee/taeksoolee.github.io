기획서가 놓은 함정 하나

기획서는 입력 필드 토큰에 text-slate-100을 넣어두고, 동시에 Method별 글자색을 text-emerald-400 같은 값으로 지정했다. 같은 CSS 속성을 두고 두 유틸리티가 충돌한다. 기획서를 쓸 때 의도한 함정이 아니라, 쓰고 나서야 드러난 구멍이다.

React와 Vue는 충돌을 스스로 발견하고 text-slate-100을 select에서 제외했다. Svelte와 Angular는 공용 입력 토큰을 그대로 쓴 뒤 Method 색상을 덧붙였다 — 최초 구현 기준으로 넷 중 둘만 색이 나왔다.

아무도 못 본 걸 잡았다

HttpErrorResponse는 statusText가 비면 생성자에서 'Unknown Error'로 강제 치환한다. HTTP/2 응답은 statusText가 항상 빈 문자열이므로, 그냥 두면 나머지 셋이 404로 표시할 상황에서 Angular만 404 Unknown Error가 된다. 지시받은 함정보다 한 겹 더 깊은 문제를 스스로 찾아 되돌렸다.

Svelte

Vue

스킬은 "UI 섹션이 3개 이상이면 컴포넌트를 분리하라"고 요구했지만, 기획서는 단일 SFC를 지시했다. 기획서를 따르고 스킬을 불채택한 뒤 그 사실을 보고했다. 지시한 우선순위를 정확히 지켰다.

Verdict · Round 1

1차 순위

결함이 해소된 뒤 남은 축은 넷이다 — 함정을 자력으로 넘었는가, 설계가 계층을 갖췄는가, 유지보수가 가능한가, 얼마나 들었는가. 코드를 읽기 전 순위와 읽은 뒤 순위가 달랐다.

1

React

자력 통과3계층

함정을 스스로 넘었고, 유일하게 3계층으로 분리했다 — 순수 헬퍼 / 상태 훅 / 뷰 컴포넌트 8개. 로직만 떼어 테스트할 수 있는 유일한 구현이고, 시간·토큰도 1위다. 673줄로 가장 길지만 그 길이는 낭비가 아니라 추상화의 비용이었다. 충돌 해결 방식은 나머지 둘을 고칠 때 그대로 가져다 썼다.

2

Vue

자력 통과1계층

함정을 스스로 넘었고 도구 호출 17회로 가장 적게 움직였다. shallowRef와 ref를 목적에 따라 갈라 쓰고, computed 17개로 표현 로직에 이름은 붙였다. 다만 컴포저블도 컴포넌트도 추출하지 않은 평면 구조라 로직만 떼어 테스트할 수 없다. 번들은 31.7 KB로 가장 작다.

Key finding · Round 2

경합 조건 — 셋은 만들었고 하나는 이미 갖고 있었다

A 요청이 진행 중일 때 B를 보내면, A의 늦은 응답이 B의 결과를 덮어써서는 안 된다. 이 문제에서 프레임워크의 성격이 가장 선명하게 갈렸다.

Angular는 1차에서 자기가 쓴 정답을 스스로 뒤집었다.

1차에서는 소요 시간을 finalize에 기록하는 것이 정답이었다. 그런데 switchMap이 들어오자 finalize가 unsubscribe에서도 실행되어 덮어쓰인 A의 시간이 B를 오염시킨다는 것을 발견하고, 결과가 확정되는 map 지점으로 옮겼다. 그리고 그 성질을 테스트로 고정했다. 조건이 바뀌자 과거의 정답을 버린 것이다.

Two-way binding

양방향 동기화 — 넷 다 순환을 구조로 막았다

Params 탭과 URL 입력이 서로를 갱신해야 한다. 재진입 플래그를 쓴 구현은 하나도 없었다. 넷 다 "순환이 코드에 존재하지 않게" 만들었고, 접근만 달랐다.

프레임워크구조커서 점프 해결
React 두 방향이 각각 reducer 전이 1회. 전이 후 새 이벤트 없이는 아무것도 재실행되지 않음 URL을 절대 재직렬화하지 않음. 미완성 문자열도 그대로 저장
Vue 단방향 명령 2개. params → setUrl 간선이 코드에 없음 키 입력을 그대로 저장, getter가 그대로 반환
Svelte 역방향이 setter를 우회해 private 필드에 직접 씀 + 정규화 비교 가드 동일. 추가로 rowsMatchQuery로 의미 불변 시 행 재생성 차단
Angular linkedSignal로 URL이 유일한 진실 원천. 역방향은 파생이 아니라 사용자 행위 정규화·재직렬화 없음 → 되쓰는 문자열이 입력과 동일해 브라우저가 no-op 처리

Angular 방식은 공짜 보너스가 있었다 — URL이 진실 원천이므로 히스토리 복원 때 url만 넣으면 params가 저절로 살아난다. 나머지 셋은 행을 따로 복원해야 한다.

ValidatorFn만 쓰면 컨트롤 하나의 값만 보이므로 superRefine의 교차 필드·중복 규칙을 표현할 수 없다. 제출 시점 safeParse만 쓰면 폼이 제출 전까지 valid라고 거짓말해 "저장 버튼은 dirty && valid일 때만"이 성립하지 않는다. Angular는 이 딜레마를 정확히 진단하고 층을 나눴다.

Consensus

넷 다 Send에 mutation을 쓰지 않았다

TanStack Query를 필수로 넣었지만, 요청 전송을 useMutation으로 감싼 구현은 하나도 없었다. 근거까지 네 곳이 독립적으로 같았다.

이유내용
동시성 모델 불일치mutation은 동시 호출을 직렬화하지 않는다 — "늦은 A가 B를 덮지 않는다"를 보장할 수 없다
취소 수단 부재useMutation은 signal을 주지 않는다. cancelQueries는 query 전용
캐시 대상이 아님임의 URL에 대한 1회성 명령이다. 키가 성립하지 않는다

대신 넷 다 같은 자리에 경계를 그었다 — "전송은 명령형, 저장은 선언형."

네트워크 호출은 2차에서 각자 만든 티켓·switchMap 구조가 그대로 담당하고, 히스토리 쓰기만 mutation으로 처리해 캐시 무효화에 연결했다. 그 결과 2차의 경합 조건 테스트가 네 구현 모두 한 줄도 바뀌지 않고 통과한다.

Key finding · Round 4

세 라운드 동안 못 옮긴 규칙이 옮겨졌다

I7 — "가장 최근 요청만 결과를 확정할 수 있다." 명백한 도메인 규칙인데, 1~3차 내내 AbortController + 티켓이나 switchMap이라는 프레임워크 인접 코드로만 표현됐다. 도메인에 담기지 않는 규칙인가, 아니면 담아본 적이 없는 것인가?

넷 다 옮겼다. 그리고 넷 다 같은 이유를 찾았다.

“티켓이 정확성을, abort가 대역폭을 담당한다.”

도메인은 “옛 시도가 결과를 확정해도 되는가”(아니오)를 결정하고, 어댑터는 “소켓을 끊을까”(예)를 결정한다. 규칙과 효과가 한 함수 안에 뭉쳐 있었을 뿐, 애초에 분리 가능한 것이었다.

Reactivity clash

가변 애그리거트 vs 네 개의 반응성 모델

DDD의 애그리거트는 보통 불변식을 지키는 가변 객체다. 그런데 네 프레임워크는 상태 변경을 저마다 다르게 다룬다. 넷의 답이 갈렸다.

Vue

프레임워크 내부 동작을 이용했다

Vue의 긴장은 반대 방향이다 — reactive()의 깊은 프록시가 편리한 대신 모든 필드를 공개 API로 만들어 팩토리를 우회할 수 있게 한다. 해법은 Object.freeze. strict mode 쓰기를 막을 뿐 아니라, Vue의 getTargetType()이 non-extensible 객체를 INVALID로 분류해 reactive()가 프록시를 씌우지 않고 원본을 반환한다. expect(reactive(req)).toBe(req)로 회귀까지 고정했다.

Angular

3차의 타협이 사라졌다

withState가 평평한 객체가 아니라 Record를 요구하고 클래스 인스턴스도 isRecord()를 통과한다는 것을 찾아냈다. 3차에 withProps로 빠져 있던 params·activeTab이 제자리로 돌아왔고, withProps엔 상태가 아닌 Subject 2개만 남았다. patchState에는 애그리거트 메서드가 만든 새 인스턴스를 넣었다 — 불변 스프레드를 쓰면 애그리거트를 우회하는 길이 열리기 때문이다.

Svelte

최대 장점이 함정이었다

$state를 쓰는 순간 그 파일은 Svelte 컴파일러를 요구한다. 즉 룬 클래스는 도메인이 아니라 어댑터다. 순수 TS로 내리는 것 외엔 선택지가 없었고, 반응성 전체를 #revision = $state(0) 카운터 하나가 지탱하게 됐다. 깨진 테스트 48개가 그 대가를 설명한다 — 전부 DOM을 한 줄도 안 쓰면서 jsdom 값을 치르던 것들이었다. “클래스인데 반응형”이 너무 쉬웠던 나머지 반응성이 필요 없는 규칙까지 빨려 들어가 있었다.

React

가변을 포기하고, 왜인지 설명했다

가변 애그리거트를 유지하려면 알림 브리지 + useSyncExternalStore의 안정 스냅샷 + persist 시점 + StrictMode 안전성을 손으로 만들어야 하고, “그건 불변 전이를 재구현하는 것”이라 포기했다. 그래도 애그리거트인 근거가 정확하다 — 순수 함수 모음과 갈리는 지점은 “상태 값을 직접 만들 수 있는가”이고, 3차 AnalyzerState는 interface라 “로딩 중인데 진행 요청 없음”을 리터럴로 만들 수 있었다.

기획서의 규칙 하나가 구조를 망가뜨렸다 — 이 문서 쪽 결함이다.

의례 방지를 위해 “심볼 하나만 re-export하는 배럴 금지”를 넣었다. React는 그 규칙을 피하려고 구현을 슬라이스 루트 index.tsx에 넣었다. features/save-request/는 파일이 index.tsx 하나뿐이고 176줄 전체가 구현이며, pages/settings/index.tsx는 192줄이다. 공개 API가 아니라 슬라이스에 내부 구조가 없는 것이다.

그리고 대가가 하나 더 있었다 — 본인들이 발견한 대로, steiger는 슬라이스 루트 index.*의 import를 분석하지 않는다. 규칙 하나가 구조를 나쁘게 만들고 도구 사각지대까지 만들었다.

구조만 놓고 보면 Vue가 가장 정돈돼 있다. 13/13 세그먼트, shared 19.0%로 최소, 배럴이 문서화돼 있고 진입점 2개로 FSD 모순을 해결했다. Svelte가 근소한 2위 — 15슬라이스로 가장 잘게 나눴지만 마스킹을 shared에 둔 것이 자기 원칙과 어긋난다. React는 구조적으로 가장 약하고 동시에 핵심 코드가 가장 우아하다 — 좋고 나쁨이 가장 뚜렷하게 갈린 구현이다.

Round 6 — 인도

구조를 다섯 번 바꿨다. 이제 그걸 쓴다

2~5차는 전부 구조를 바꾸는 라운드였다. 6차는 처음으로 그냥 기능을 만든다. 구조를 어떻게 쓸지는 지시하지 않았다 — 실무는 “FSD로 해주세요”가 아니라 “이거 만들어주세요”로 오기 때문이다.

The hypothesis

모양이 다른 기능 세 개

5차에서 Svelte가 정확히 지적했다 — “secret은 횡단 관심사라 FSD에 불리했다.” 기능 하나로 잰 것이 한계였다. 그래서 모양을 셋으로 나눴다.

F1 · 수직

히스토리 항목 고정

한 관심사 안에서 끝나야 할 기능. 고정된 항목은 보관 상한 정리에서 제외된다 — 4차에 정의한 불변식 I4가 바뀐다.

F2 · 신규 관심사

저장된 요청 태그

새 세로줄을 하나 더하는 비용. 별도 슬라이스로 만들지 기존 필드로 둘지는 일부러 지시하지 않았다.

F3 · 횡단

커맨드 팔레트 (⌘K)

컬렉션·히스토리·환경을 한 입력창에서. 모든 관심사에 걸린다. 5차 secret과 같은 모양의 비교 기준선.

예측은 이랬다 — 격차(F3 ÷ F1)가 크면 구조가 값을 한 것이다. 수직 기능은 싸고 횡단 기능만 비싸야 한다.

Payoff

4차에 묻어둔 투자가 여기서 회수됐다

F1은 4차에 도메인으로 끌어올린 불변식 I4를 개정하는 과제였다. “히스토리 길이는 상한을 넘지 않는다”가 “고정되지 않은 항목에만 적용된다”로 바뀐다. 넷 다 도메인 한 곳에서 흡수했다.

Methodology

측정 장치가 결과를 오염시켰다

이 문서가 저지른 가장 큰 방법론 실패다. 무엇을 잴지 미리 알려줬더니 네 구현 중 셋이 그 지표에 맞춰 설계를 바꿨다.

출처실제로 일어난 왜곡
React430줄짜리 파일을 쪼개고 싶었지만 F1 파일 수가 늘까 봐 미뤘다. 그 파일이 더 커진 채로 인도
Vue팔레트를 지연 마운트하려면 컴포넌트를 쪼개야 했는데 F3 수가 늘어서 포기. 결과적으로 앱 시작 시 쿼리 3개가 무조건 실행됨
Angular“측정 대상이 되는 순간 리팩터링 결정이 오염됩니다.” 죽은 포트 메서드를 지운 대가로 격차가 0.71 → 0.50으로 나빠졌다 — “지표 때문에 남겼다면 조작이고, 지운 건 정직하지만 사실을 만들었다”
Angular“지표가 파일 수라서 한 파일에 몰아넣는 유인이 생기고, 저도 거기 걸렸습니다.” 태그 편집을 목록 행에 넣어 한 파일이 +131줄

Svelte는 지표를 조작할 방법을 정확히 알면서 하지 않았다고 밝혔다.

“pinned?(optional) + 정렬을 컴포넌트에서 + 배럴 우회하면 5÷3 = 1.67로 보기 좋아진다. §6.1은 ‘파일을 잘게 쪼개 지표를 좋게 하기’는 잡지만 ‘규칙을 지켜 파일이 느는 것’은 구분하지 못한다.”

이 발견 때문에 7차부터는 측정 계획을 사전에 공개하지 않는다. 기능만 주고, 측정은 스냅샷 대조로 사후에 한다.

Spec defect

한 줄짜리 규칙이 세 라운드 동안 피해를 냈다

5차 §7 — “심볼 하나만 re-export하는 배럴은 금지.” 의례를 막으려고 넣은 규칙이었다.

4차: React가 규칙을 피하려고 구현을 슬라이스 루트 index.tsx에 넣었고, steiger가 그 6개 파일을 통째로 무검사했다.
5차: 그 결과 React의 슬라이스 6개가 평면이 되고 구조 점수가 깎였다.
6차: React·Vue·Angular가 동시에 같은 충돌을 보고했다.

Angular의 진단이 가장 정확하다 — “팔레트의 자연스러운 자리는 features/command-palette인데, 배럴이 없으면 자체 규칙이 막고 배럴을 만들면 §7 위반이다. 두 규칙이 겹쳐 features 레이어가 app에 닫혀 있다. 결과적으로 옳은 자리에 뒀지만, 옳은 자리를 규칙이 골라 준 것이지 내가 고른 게 아니다.”

React의 정리 — “도메인 함수 30개짜리 배럴과 소비자 하나짜리 컴포넌트를 같은 규칙으로 묶으면 공개 표면이라는 개념이 망가진다.” 7차 기획서에서 이 규칙은 폐기됐다.

이 문서는 여덟 번 예측했고 여덟 번 틀렸다. 그게 여기서 가장 값진 부분이다.

1차엔 “밀도”와 “설계”를 혼동했고, 5차엔 FSD가 이길 줄 알았고, 6차엔 격차가 1보다 클 줄 알았고, Vue의 E2E 실패 원인을 엉뚱한 곳에서 찾았으며, 8차엔 배럴 결함을 “넷 중 셋이 찾았다”고 적었다가 Angular의 §2.4를 읽고 만장일치로 고쳤다. 매번 코드를 직접 읽고 나서 판단이 바뀌었고, 매번 에이전트들이 더 나은 해석을 내놨다.

그리고 이 문서 자체가 실험 대상을 오염시켰다. 지표를 미리 공개하자 넷 중 셋이 그 지표에 맞춰 설계를 바꿨고, 한 줄짜리 배럴 규칙은 세 라운드 동안 피해를 냈으며, “공개 API로만 접근하라”와 “순수 계층은 I/O를 모른다”가 서로를 무력화하며 다섯 라운드 동안 초록으로 앉아 있었다. 그리고 8차에 드러났듯 같은 규칙이 네 생태계 전부에서 트리 셰이킹까지 막고 있었다 — 다섯 라운드 동안 아무도 재보지 않았기 때문에 아무도 몰랐다.

7차가 준 답은 이것이었다 — 처방은 검사할 수 있는 주장을 만들고, 처방의 부재는 그것을 검사할 시간을 준다. 네 구현은 공식 린터를 만장일치로 지웠지만 타입 게이트는 넷 다 남겼다. 강제되지 않을 때 무엇을 남기는가가 그 처방이 값을 했는지에 대한 유일하게 정직한 투표다.

8차가 덧붙인 답은 더 불편하다 — 일곱 라운드 동안 쌓은 산문은 단 한 번도 측정된 적이 없었다. Svelte의 표현으로, “라운드마다 산문은 상속되고 숫자는 상속되지 않았습니다.” 그리고 “구조는 실제로 무거운 것에 대해 아무 말도 하지 않습니다” — 일곱 라운드의 규칙은 전부 네 구현이 직접 쓴 7%의 바이트를 다스렸고, 나머지 93%를 차지하는 의존성 그래프에 대해서는 어느 라운드도 질문을 던지지 않았다. 마지막에 네 구현이 만장일치로 찾아낸 결함이 하필 이 문서가 처방한 규칙이었던 것은 우연이 아니다. 검사되지 않는 처방은 시간이 지날수록 비용만 남긴다.

Verdict

원래 질문으로 — AI로 개발할 때 무엇이 다른가

이 연구는 “어느 프레임워크가 낫냐”를 물으려고 시작한 것이 아니다. AI에게 맡겨 개발할 때 네 프레임워크가 어떻게 다른가를 보려고 시작했다. 여덟 라운드를 그 축으로 다시 자르면, 각 라운드는 AI 개발의 한 국면을 모형화한 것이 된다.

이건 프레임워크가 준 것이 아니라 순수 계층 분리가 준 것이고, 네 구현 모두 해냈다. 프레임워크 없이 도는 테스트 비율은 Svelte 93% · Vue 82% · Angular 79% · React 73%다 (각각 742/799 · 283/347 · 215/271 · 163/222). AI에게 “알아서 고쳐봐”라고 말할 수 있게 해 주는 것이 정확히 이 숫자다.

반대로, 넷이 똑같이 잘한 것도 읽어서 확인했다 — 디스크에서 읽은 것은 타입이 아니다.

네 앱 모두 IndexedDB 값 타입을 unknown으로 두고, 복원 함수가 보증한 뒤에야 도메인 값이 되게 했다(I9). Angular의 표현 — “디스크에서 읽은 것은 타입이 아니라 바이트다. 여기서 도메인 타입을 주장하면 그 거짓말이 I9을 무력화한다.”

그리고 전송·취소·경합의 핵심도 넷 다 같은 결론에 도달했다 — 티켓이 정확성을, abort가 대역폭을 맡는다. 가장 응축된 것은 React의 Exchanges 63줄로, 티켓 하나만 하고 포트를 콜백으로 주입받아 도메인이 AbortController라는 이름조차 모른다. 가장 강한 것은 Angular의 SendCommand로, private 생성자 때문에 “승인 없이 전송”을 타입 단계에서 표현할 수 없다.

두 순위가 어긋나는 지점을 그대로 남겨 둔다.

라운드 성적으로 본 AI 적합성은 Svelte(위임) · Angular(지시) · React(싼 일반형) · Vue(함정)이고, 완성된 코드베이스로 본 순위는 Svelte · Angular · Vue · React다. 위 둘은 같고 아래 둘이 뒤바뀐다.

읽어 보면 이유가 분명하다 — React는 작업 비용이 싸고(누적 1.91M, 최저) Vue는 결과물이 낫다 (변경 파급 795줄 최소, 테스트 결합 1개, 레이어 균형 최고). React의 대가는 운영이 아니라 표면에 있다: 의존성 17개, 커스텀 심볼 282개, shadcn 23파일 직접 소유, 그리고 검증의 27%가 jsdom을 탄다. “싸게 만든다”와 “물려받기 좋다”가 같은 것이 아니라는 뜻이고, 둘 중 무엇이 중요한지는 프로젝트가 정한다.

그리고 구조는 처음부터 주는 편이 낫다 — 단, 확인되는 것만.

4차는 기능을 하나도 안 늘리고 프레임워크당 35만 토큰을 썼다. “구조를 옮기는 일은 기능을 만드는 일만큼 비싸다.” 그리고 7차에 강제를 전부 거두자 네 구현이 만장일치로 계층과 타입 게이트를 남기고 스타일 린터만 지웠다. 구조가 짐이었으면 그때 접었을 것이다.

기준은 “미리 하느냐”가 아니라 “어겼을 때 보이느냐”다. 살아남은 규칙(도메인이 프레임워크를 import하지 않는다 · 금지 전역을 모른다 · 결과를 타입으로 나눈다)은 전부 grep이나 tsc 한 번에 걸린다. 다섯 라운드 동안 피해를 낸 배럴 규칙은 실패가 번들 안에만 나타나서 아무도 보지 못했다.

이 목적에 대해 이 연구가 답하지 못한 것.

프레임워크당 N=1이다 — 순위 1~3점 차이는 노이즈와 구분되지 않는다. 에이전트 품질과 프레임워크 품질이 분리되지 않았다 — 보고서 문장의 날카로움 차이는 프레임워크 속성이 아닐 가능성이 크다. 검증 가능한 사실(PrimeVue 0.38 ms · Vue 프로파일러 · Angular 코어 112 kB · 룬 용접 · React 19 window.load)만 프레임워크 사실로 쓸 것.

모델이 하나다. 특히 “학습 데이터가 많아 React가 유리하다”는 모델이 바뀌면 달라질 수 있는 항목이다. 앱도 하나다 — 백엔드 없는 5화면. SSR · 대용량 데이터 · 실시간 · 팀 협업은 전혀 재지 않았다.

그리고 가장 큰 공백 — 긴 세션에서의 붕괴를 재지 않았다. 각 라운드는 독립 실행이었고, “AI가 100턴째에 자기 구조를 잊는가”는 측정하지 않았다. 실제 개인 개발에서 가장 자주 일어나는 일인데 이 연구에는 빠져 있다.

Angular가 여덟 중 다섯 라운드에서 가장 비싸다누적 2,283,600 토큰으로 최다이며, 가장 싼 React보다 1.20배다. 2차에 이 문서가 “감점할까” 물었던 그 차이가 여덟 라운드 내내 유지됐다. 감점하지 않은 것은 옳았다 — 4·5·6·8차 1위가 같은 구현이다.
